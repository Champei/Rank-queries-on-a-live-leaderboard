## What the function must return

The Fenwick tree stores player counts over `U = scores.size()` sorted, unique score coordinates. `scores` and `cnt` are zero-based; `bit` is one-based. Let

`P(j) = cnt[0] + cnt[1] + ... + cnt[j-1]`, with `P(0) = 0`.

Thus, `P(j)` counts players in the first `j` coordinates. Counts are nonnegative, so `P` never decreases, even when some coordinates have zero players.

`select_score(position)` receives a one-based position from the top of the leaderboard. It rejects `position <= 0` or `position > total`. It converts a valid position into an ascending target:

```cpp
ll target = total - position + 1;
```

Call this original target `k`. We need the smallest one-based coordinate `j` with `P(j) >= k`. Its score is `scores[j-1]`.

## How the code searches

The code starts with `at = 0`. It finds `LOG` such that `2^LOG` is the largest power of two no greater than `U`, then tries these powers in decreasing order:

```cpp
for(ll i=LOG; i>=0; i--) {
    ll step = 1LL << i;
    ll next = at + step;
    ++step_count;
    if (next <= (ll)scores.size() && bit[next] < target) {
        target -= bit[next];
        at = next;
    }
}
return scores[at];
```

A valid position implies that at least one player exists, so `U` is positive when this search runs.

## Loop invariant and proof

Let `b` be the largest prefix length for which `P(b) < k`. It exists because `P(0) = 0 < k`. Also, `b < U`, since `P(U) = total >= k`.

Before testing a power `step`, the following statements hold:

1. `P(at) < k` and `target = k - P(at)`. We have skipped a prefix that does not yet reach the original target.
2. `at` is a multiple of `2 * step`.
3. `at <= b < at + 2 * step`. The largest prefix we can skip is inside this interval.

**Initially:** `at = 0` and `target = k`. If the first power is `S`, then `S <= U < 2S`. Therefore `0 <= b < 2S`, and all three statements hold.

**Why `bit[next]` is the right block:** because `at` is a multiple of `2 * step`, `next = at + step` has lowest set bit equal to `step`. The Fenwick entry at `next` therefore stores exactly the count between prefix lengths `at` and `next`:

`bit[next] = P(next) - P(at)`.

Consequently, `bit[next] < target` is equivalent to `P(next) < k`.

**If the test succeeds:** `next` is a prefix we can skip, so `b >= next`. We set `at = next` and subtract the skipped block from `target`. This preserves `target = k - P(at)`. The previous upper bound gives `b < new_at + step`.

**If the test fails:** either `next > U`, or `P(next) >= k`. In both cases `b < next = at + step`, so we keep `at` and `target`.

After either case, `at <= b < at + step`. When the power is halved, this is exactly the interval needed for the next iteration. The alignment condition also holds: the new `at` is a multiple of the old `step`, which is twice the next power.

**At the end:** after testing `step = 1`, we have `at <= b < at + 1`. Both are integers, so `at = b`. Therefore

`P(at) < k <= P(at + 1)`.

The smallest one-based coordinate reaching `k` is `at + 1`. Its zero-based index is `at`, which explains the code's return value `scores[at]`.

The comparison must be strict `<`. If a block reaches the target exactly, the answer lies inside that block; skipping it could move past the answer.

## Worked example, including zero-count coordinates

Start with the allowed universe `[50,10,30,10,40,20]`. After sorting and removing duplicates, insert players with scores `[10,30,40,40,10,40]`:

| One-based coordinate | Score | Count | Prefix count | Fenwick entry |
|---|---:|---:|---:|---:|
| 1 | 10 | 2 | 2 | 2 |
| 2 | 20 | 0 | 2 | 2 |
| 3 | 30 | 1 | 3 | 1 |
| 4 | 40 | 3 | 6 | 6 |
| 5 | 50 | 0 | 6 | 0 |

Here `U = 5`, `total = 6`, and descending scores are `[40,40,40,30,10,10]`.

For `select_score(3)`, the ascending target is `k = 6 - 3 + 1 = 4`. Start with `at = 0`, `target = 4`, and try powers `4,2,1`:

| Power | Candidate `next` | Test | Result |
|---|---:|---|---|
| 4 | 4 | `bit[4] = 6 < 4` is false | Keep `at = 0`, `target = 4` |
| 2 | 2 | `bit[2] = 2 < 4` is true | Set `at = 2`, `target = 2` |
| 1 | 3 | `bit[3] = 1 < 2` is true | Set `at = 3`, `target = 1` |

Return `scores[3] = 40`. Indeed, `P(3) = 3 < 4 <= P(4) = 6`.

The empty score coordinate 20 is included in the skipped prefix without causing a problem. Zero counts make equal adjacent prefix sums, but they do not break monotonicity. Searching for the first prefix reaching `k` still gives an occupied score coordinate.

The strict comparison also matters in this same example: `select_score(5)` gives `k = 2`. At candidate 2, `bit[2] = 2`, so the code must not skip that block. It eventually returns 10, the correct fifth score from the top.

## Time complexity

Finding `LOG` takes `O(log U)` iterations. The descent then performs exactly `floor(log2 U) + 1` tests, each with constant work. It reads Fenwick entries directly rather than calling `prefix()` at every step. Therefore `select_score` takes `O(log U)` time and `O(1)` extra space. For `U = 1`, it performs one test.

## Why the allowed universe must be known beforehand

Coordinates come from the allowed score universe, not just the players currently present. In our example, 20 and 50 retain coordinates even though their counts are zero.

Every score that a replay may insert must belong to this universe. For example, 35 has no coordinate in `[10,20,30,40,50]`, so `accepts(35)` returns false and `update(35,1)` throws an error. Inserting a new coordinate between 30 and 40 would shift later indices and change the Fenwick block layout. The existing arrays cannot support that by one ordinary update.

To support 35, construct a new Fenwick tree with a universe including 35 and reinsert the current player scores, for example through `rebuild()`. The application avoids this problem by preparing all allowed scores from 0 through 10000 before replay begins.
